Human-in-the-Loop (HITL) + User Context Memory as shared services around your three CrewAI agents:

1. Weather Agent — retrieves current weather.
2. Weather Forecast Agent — retrieves upcoming weather forecasts.
3. FAQ Agent — answers weather-related questions using your FAQ/RAG knowledge base.

The key design principle is that all three agents share the same validated user context, while the approval service controls consequential actions such as sending weather notifications.

## 1. Proposed architecture

Client / n8n / MCP Client

Question + authenticated user + conversation session

FastAPI — Conversation Orchestrator

Authentication · Input guardrails · Intent routing

Context Memory

Redis: preferences, recent conversation, last city

CrewAI

Current weather · Forecast · FAQ agents

Decision / Action Gate

Read-only response → return directly; consequential action → request human approval

Approval Service + Weather Tools

Validate decision · Execute once · Audit · Update context

Important: You do not need human approval for every weather query. The current weather, forecast, and FAQ agents should generally answer automatically. HITL is needed when an action requires consent, such as sending a bulk weather alert, or when the application needs clarification.

## 3. Implement user context memory

Use Redis to store the conversation context and a short history. The context should be loaded before calling the crew and included in the task inputs.

`app/services/context_memory.py`

```
import json
from redis.asyncio import Redis


class ContextMemory:
    def __init__(self, redis: Redis):
        self.redis = redis

    def _context_key(self, user_id: str, session_id: str) -> str:
        return f"weather:context:{user_id}:{session_id}"

    async def get_context(
        self,
        user_id: str,
        session_id: str,
    ) -> dict:
        data = await self.redis.get(
            self._context_key(user_id, session_id)
        )
        return json.loads(data) if data else {}

    async def update_context(
        self,
        user_id: str,
        session_id: str,
        updates: dict,
    ) -> dict:
        context = await self.get_context(user_id, session_id)
        context.update(updates)

        await self.redis.set(
            self._context_key(user_id, session_id),
            json.dumps(context),
            ex=86400,
        )
        return context

    async def add_message(
        self,
        user_id: str,
        session_id: str,
        role: str,
        content: str,
    ) -> None:
        key = f"weather:history:{user_id}:{session_id}"

        await self.redis.rpush(
            key,
            json.dumps({"role": role, "content": content}),
        )
        await self.redis.ltrim(key, -10, -1)
        await self.redis.expire(key, 86400)

    async def get_history(
        self,
        user_id: str,
        session_id: str,
    ) -> list[dict]:
        key = f"weather:history:{user_id}:{session_id}"
        messages = await self.redis.lrange(key, 0, -1)
        return [json.loads(message) for message in messages]
```

This stores the last ten messages and a separate context object. In production, validate the fields you allow into persistent context rather than letting arbitrary model output overwrite it.

For example:

```
{
  "preferred_city": "Delhi",
  "temperature_unit": "celsius",
  "last_intent": "forecast",
  "last_query": "Will it rain tomorrow?"
}
```

Use the authenticated `user_id` from your backend identity, not an untrusted ID supplied in the request body. A session should belong to that user, and the context must never be shared across different users.

## 4. Pass context to all three CrewAI agents

When a user asks a follow-up question, retrieve the memory first and supply it as part of the crew's inputs.

For example, extend the task description in your existing crew:

```
from crewai import Task

weather_task = Task(
    description="""
    Answer the user's request: {question}

    User context:
    {user_context}

    Recent conversation:
    {conversation_history}

    Rules:
    - Use the explicit city in the latest question if provided.
    - Otherwise, use the remembered city when appropriate.
    - Ask for clarification if the city is ambiguous.
    - Use weather tools for current or forecast facts.
    - Use the FAQ knowledge base for general weather questions.
    - Never invent weather data.
    """,
    expected_output="A relevant, accurate weather response.",
    agent=weather_agent,
)
```

Apply the same context inputs to the forecast and FAQ tasks, adapting their instructions to their respective responsibilities.

Your existing agent-selection logic can decide which task or crew to execute. For example:

- “What's the weather today?” → Weather Agent.
- “Will it rain over the next five days?” → Weather Forecast Agent.
- “What does a UV index mean?” → FAQ Agent.
- “Will it rain tomorrow there?” → Forecast Agent with the remembered city, if unambiguous.

You do not need to run all three agents for every question.

## 5. Implement the approval service

Use the approval service only when a real action needs consent. For example, the agent may prepare a severe-weather notification, but it must not have permission to send it directly.

`app/services/approval_service.py`

```
import json
import uuid
from redis.asyncio import Redis


class ApprovalService:
    def __init__(self, redis: Redis):
        self.redis = redis

    async def create_request(
        self,
        user_id: str,
        session_id: str,
        action: str,
        payload: dict,
    ) -> dict:
        approval_id = str(uuid.uuid4())

        request = {
            "approval_id": approval_id,
            "user_id": user_id,
            "session_id": session_id,
            "action": action,
            "payload": payload,
            "status": "pending",
        }

        await self.redis.set(
            f"weather:approval:{approval_id}",
            json.dumps(request),
            ex=1800,
            nx=True,
        )

        return request

    async def get_request(self, approval_id: str) -> dict | None:
        data = await self.redis.get(
            f"weather:approval:{approval_id}"
        )
        return json.loads(data) if data else None
```

This creates a pending approval request with a 30-minute expiry. We also need a safe way to approve it.

Add a method that atomically claims a pending request. This prevents two concurrent approval requests from both initiating the same action.

```
        async def claim_request(
        self,
        approval_id: str,
        user_id: str,
        decision: str,
    ) -> dict:
        key = f"weather:approval:{approval_id}"

        script = """
        local raw = redis.call('GET', KEYS[1])
        if not raw then return 'NOT_FOUND' end

        local req = cjson.decode(raw)

        if req['user_id'] ~= ARGV[1] then
            return 'FORBIDDEN'
        end

        if req['status'] ~= 'pending' then
            return 'NOT_PENDING'
        end

        if ARGV[2] == 'approve' then
            req['status'] = 'executing'
        else
            req['status'] = 'rejected'
        end

        req['decision'] = ARGV[2]
        req['approver_id'] = ARGV[1]

        redis.call(
            'SET', KEYS[1], cjson.encode(req), 'EX', 1800
        )

        return cjson.encode(req)
        """

        result = await self.redis.eval(
            script, 1, key, user_id, decision
        )

        if result == "NOT_FOUND":
            raise ValueError("Approval request not found or expired")
        if result == "FORBIDDEN":
            raise PermissionError("Not authorized to approve")
        if result == "NOT_PENDING":
            raise ValueError("Approval already processed")

        return json.loads(result)
```

The example permits only the original user to approve. For administrative weather alerts, replace that policy with an explicit role/permission check so an authorized reviewer can approve on behalf of the application.

A production version should also record durable audit history and handle failed executions and retries. Pass `approval_id` as an idempotency key to the downstream notification service; a Redis state transition alone cannot guarantee exactly-once delivery if the process crashes during an external API call.

## 6. Create the FastAPI approval endpoints

The UI can show a pending alert with Approve and Reject actions. When the user responds, the backend validates the request and executes the action only if approved.

`app/api/routes/approvals.py`

```
from typing import Literal

from fastapi import APIRouter, Depends, HTTPException
from pydantic import BaseModel

router = APIRouter(prefix="/approvals", tags=["Approvals"])


class ApprovalDecision(BaseModel):
    decision: Literal["approve", "reject"]


@router.post("/{approval_id}")
async def decide_approval(
    approval_id: str,
    body: ApprovalDecision,
    # Replace these with your application's dependencies.
    user=Depends(get_current_user),
    approval_service=Depends(get_approval_service),
    notification_service=Depends(get_notification_service),
):
    try:
        request = await approval_service.claim_request(
            approval_id=approval_id,
            user_id=str(user.id),
            decision=body.decision,
        )
    except PermissionError:
        raise HTTPException(403, "Not authorized")
    except ValueError as exc:
        raise HTTPException(409, str(exc))

    if body.decision == "reject":
        return {"status": "rejected"}

    try:
        if request["action"] != "send_weather_alert":
            raise HTTPException(400, "Unsupported action")

        await notification_service.send_weather_alert(
            **request["payload"],
            idempotency_key=approval_id,
        )

        await approval_service.mark_completed(approval_id)

        return {"status": "completed"}

    except Exception:
        # Implement a durable retry/reconciliation mechanism.
        # Do not reset blindly to pending: the external service
        # may have accepted the notification before the error.
        raise HTTPException(
            502, "Execution outcome requires reconciliation"
        )
```

This endpoint illustrates the flow; it assumes you add `mark_completed()`, the dependencies, and an idempotent notification client to your project. Persisting approval and execution records in PostgreSQL is preferable for production, particularly when notifications must be auditable.

## 7. Connect context memory, CrewAI, and HITL

Your conversation service should perform these operations in order:

1. Load context and recent conversation from Redis.
2. Resolve the request to the current-weather, forecast, or FAQ agent.
3. Call the selected CrewAI task with the question and context.
4. Return ordinary answers immediately.
5. For an action requiring consent, create an approval request and return its ID.
6. Update conversation history after the interaction.

A simplified orchestration example:

`app/services/conversation_service.py`

```
class ConversationService:
    def __init__(
        self,
        context_memory,
        weather_crew,
        approval_service,
    ):
        self.context_memory = context_memory
        self.weather_crew = weather_crew
        self.approval_service = approval_service

    async def chat(
        self,
        user_id: str,
        session_id: str,
        question: str,
    ) -> dict:
        context = await self.context_memory.get_context(
            user_id, session_id
        )
        history = await self.context_memory.get_history(
            user_id, session_id
        )

        result = await self.weather_crew.run(
            question=question,
            user_context=context,
            conversation_history=history,
        )

        # Example contract: an explicit, validated action proposal
        # is returned separately from the user-facing answer.
        if result.get("proposed_action") == "send_weather_alert":
            request = await self.approval_service.create_request(
                user_id=user_id,
                session_id=session_id,
                action="send_weather_alert",
                payload=result["action_payload"],
            )

            return {
                "status": "pending_approval",
                "approval_id": request["approval_id"],
                "message": "Please review the proposed weather alert.",
            }

        answer = result["answer"]

        await self.context_memory.add_message(
            user_id, session_id, "user", question
        )
        await self.context_memory.add_message(
            user_id, session_id, "assistant", answer
        )

        return {"status": "completed", "answer": answer}
```

Here, `weather_crew.run()` is an application-level wrapper you would implement around your existing CrewAI routing and `kickoff()` call. Standard CrewAI output does not automatically contain the `proposed_action` structure shown above; define and validate that structured output explicitly. Never let arbitrary LLM-generated text trigger an external action.

## 8. How the complete interaction works

1\. User request

“Check the forecast for Delhi and prepare a severe-weather alert.”

2\. CrewAI execution

The forecast agent retrieves the forecast. The FAQ agent can provide relevant guidance if required. The current-weather agent is invoked only if needed.

3\. Approval required

The backend stores the proposed notification and returns `pending_approval` with an `approval_id`. Nothing is sent yet.

4\. Human decision

The authenticated reviewer approves or rejects the request through the approval API.

5\. Controlled execution

If approved, the backend claims the request, sends the notification using an idempotency key, records completion, and updates the conversation context.

## 9. Where does CrewAI's `human_input=True` fit?

You can still use `human_input=True` on a CrewAI task when a person can provide feedback while the crew is running.

For your FastAPI-based application, though, I would use the explicit approval service for the notification workflow. It separates agent reasoning from authorization and lets a user respond through a UI, REST API, n8n, or another client without keeping the original HTTP request open.

My implementation recommendation: build Redis context memory first, pass context into all three agents, and then add the approval flow for one controlled action: sending a weather notification. Once that works, add tests for user isolation, expired approvals, rejected requests, concurrent approval attempts, and notification retries.
